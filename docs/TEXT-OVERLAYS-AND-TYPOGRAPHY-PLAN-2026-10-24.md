# Text overlays and typography: product specification and implementation queue

## T4m · Unicode default-ignorable font-warning accuracy · 26 October 2026

**Specific extension of #751's false missing-glyph fix:** The font-coverage checker manually suppressed Bidi controls, emoji ZWJ and variation selectors, but omitted invisible emoji tag characters U+E0020–E007F, ZERO WIDTH SPACE U+200B and COMBINING GRAPHEME JOINER U+034F. These can be semantically essential to a composed grapheme yet need no standalone font-outline mapping. Checking their `cmap` entries as independent visible letters produced misleading missing-font warnings for valid authored sequences such as England's emoji tag flag. Use the standard Unicode `Default_Ignorable_Code_Point` property to skip only non-ink codepoints; preserve warnings for a genuinely missing flag *base* U+1F3F4, visible snowman U+2603 and combining acute accent U+0301. Tests use actual Unicode control scalars and the existing synthetic font cmap, leaving native paint/export, private font data, recipes, and renderer/worker consistency unchanged. This is a Unicode property-based *diagnostic* check, not confirmation of coloured emoji, OS font fallback, or contextual shaping.

## T4l · OpenType maximum-glyph consistency for font diagnostics · 26 October 2026

**Reproduced binary-font metadata false positive:** The Unicode `cmap` reader correctly verifies nonzero glyph indices and a 16-bit maximum, but ignored the font's own `maxp.numGlyphs`. The OpenType [maximum-profile specification](https://learn.microsoft.com/en-us/typography/opentype/spec/maxp) gives the actual number of available glyph slots. A format-12 group could therefore map `🌈` to glyph index **9** while `maxp` reports only **5** glyphs, causing the UI to falsely claim that this typeface contains the character. The bounded parser now reads `maxp` version 0.5/1.0 when present, rejects malformed counts and checks both format-4 and format-12 indices against the actual font. Fonts with independently valid `cmap` but no `maxp` retain source-fixture/legacy compatibility; a verified native FontFace load remains the authority for user-provided font validity. Binary regression cases cover count **5 vs 10**, absent version, malformed version, BMP index outside count and retained true mapped Latin letters. No raw font bytes are persisted, no typography recipe or rasterizer is altered, and this is **glyph-ID plausibility, not evidence of contextual shaping or OS colour emoji support**. Exact-head focused CI qualifies the source correction; no heavyweight screenshot workflow is warranted for metadata-only code.

## T4j · Full Unicode and BMP OpenType cmap coverage, 26 October 2026

**Concrete, independently fixture-reproducible font-coverage deficiency:** Before this change, the OpenType coverage reader chose Unicode `cmap` format 12 over format 4 and ignored format 4 entirely. Valid fonts can include a supplementary format-12 map that does **not** duplicate every format-4 BMP glyph, so the UI incorrectly claimed that actual covered Latin letters were absent. A source-level fixture now builds one SFNT with format 4 covering `A–Z` and format 12 covering `🌈` only. Correct `has()` returns true for both; the previous code returned false for `A`. The parser separately bounds and validates each supported subtable, unions actual nonzero glyph mappings, and permits format-4 fallback if a format-12 candidate is malformed, without assuming unknown means absent. Existing single-table 27 bundled-font tests remain untouched; malformed dual-table cases are independently checked. No font-byte retention, network operations, private import rewrite, recipe modification or renderer/worker/export pixel change. **Cmap coverage indicates codepoint mapping, not contextual shaping quality, multicolour emoji availability or actual Android font-fallback behaviour.**

## T4i · Invisible Unicode control/font coverage accuracy, 26 October 2026

**Source-reproduced diagnostics mismatch:** `missingFontCodepoints` correctly ignores variation selectors and several Unicode formatting marks, but not LRM U+200E, RLM U+200F, ALM U+061C, WJ U+2060 or FEFF, even though these codes have no standalone glyph ink. A font whose `cmap` correctly lacks them therefore falsely receives a "typeface does not contain" warning when editing valid bidirectional text. The existing `canCurveText` native Bidi guard included LRM/RLM since #748 but missed ALM, so an otherwise Latin/digit marked line could still split into isolated curved glyphs. This correction shares a narrow, explicit no-ink control range in the font checker and extends the native whole-run guard to ALM. Actual missing visible codepoints continue to be reported. Targeted Node tests verify absence of false notices, a genuine missing snowman, one native fill for marked text, preserved editable curve and same whole-line hit. No font binaries, recipe, renderer/worker/export or private-file transport changes. **Do not interpret a `cmap` check as proof of shaping or authentic OS font glyph coverage.**

## T4h · Invisible Bidi controls on curves and rainbow stops, 26 October 2026

**Reproduced text-layout semantics bug:** The canonical complex-script guard included native RTL letters, Unicode Bidi embeddings/isolates and ZWNJ but omitted `U+200E LEFT-TO-RIGHT MARK` and `U+200F RIGHT-TO-LEFT MARK`. Thus a Latin/numeric line containing only those invisible direction controls was eligible for per-grapheme curved painting, which discards the native whole-line Bidi resolution those marks exist to request. The straight rainbow-letter segmentation also treated such non-ink graphemes as authored letters, consuming one ROYGBIV hue and shifting all subsequent visible glyph colours. The narrow fix places LRM/RLM in the native whole-line curve fallback and excludes pure Bidi formatting controls from *colour-index advances* while keeping their unchanged full-string Canvas paint and measured spans. Focused tests use actual Unicode control scalars in curved scene/one-native-fill/selection and next-hue assertions. Ordinary unmarked Latin curves, scripts, font loading, canonical recipe, Undo and renderer/worker/export source remain unchanged. No claim of a full Bidi visual-run colour resolver or Android/IME acceptance.
