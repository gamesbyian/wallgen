# Text overlays and typography: product specification and implementation queue

## T4j · Full Unicode and BMP OpenType cmap coverage, 26 October 2026

**Concrete, independently fixture-reproducible font-coverage deficiency:** Before this change, the OpenType coverage reader chose Unicode `cmap` format 12 over format 4 and ignored format 4 entirely. Valid fonts can include a supplementary format-12 map that does **not** duplicate every format-4 BMP glyph, so the UI incorrectly claimed that actual covered Latin letters were absent. A source-level fixture now builds one SFNT with format 4 covering `A–Z` and format 12 covering `🌈` only. Correct `has()` returns true for both; the previous code returned false for `A`. The parser separately bounds and validates each supported subtable, unions actual nonzero glyph mappings, and permits format-4 fallback if a format-12 candidate is malformed, without assuming unknown means absent. Existing single-table 27 bundled-font tests remain untouched; malformed dual-table cases are independently checked. No font-byte retention, network operations, private import rewrite, recipe modification or renderer/worker/export pixel change. **Cmap coverage indicates codepoint mapping, not contextual shaping quality, multicolour emoji availability or actual Android font-fallback behaviour.**

## T4i · Invisible Unicode control/font coverage accuracy, 26 October 2026

**Source-reproduced diagnostics mismatch:** `missingFontCodepoints` correctly ignores variation selectors and several Unicode formatting marks, but not LRM U+200E, RLM U+200F, ALM U+061C, WJ U+2060 or FEFF, even though these codes have no standalone glyph ink. A font whose `cmap` correctly lacks them therefore falsely receives a "typeface does not contain" warning when editing valid bidirectional text. The existing `canCurveText` native Bidi guard included LRM/RLM since #748 but missed ALM, so an otherwise Latin/digit marked line could still split into isolated curved glyphs. This correction shares a narrow, explicit no-ink control range in the font checker and extends the native whole-run guard to ALM. Actual missing visible codepoints continue to be reported. Targeted Node tests verify absence of false notices, a genuine missing snowman, one native fill for marked text, preserved editable curve and same whole-line hit. No font binaries, recipe, renderer/worker/export or private-file transport changes. **Do not interpret a `cmap` check as proof of shaping or authentic OS font glyph coverage.**

## T4h · Invisible Bidi controls on curves and rainbow stops, 26 October 2026

**Reproduced text-layout semantics bug:** The canonical complex-script guard included native RTL letters, Unicode Bidi embeddings/isolates and ZWNJ but omitted `U+200E LEFT-TO-RIGHT MARK` and `U+200F RIGHT-TO-LEFT MARK`. Thus a Latin/numeric line containing only those invisible direction controls was eligible for per-grapheme curved painting, which discards the native whole-line Bidi resolution those marks exist to request. The straight rainbow-letter segmentation also treated such non-ink graphemes as authored letters, consuming one ROYGBIV hue and shifting all subsequent visible glyph colours. The narrow fix places LRM/RLM in the native whole-line curve fallback and excludes pure Bidi formatting controls from *colour-index advances* while keeping their unchanged full-string Canvas paint and measured spans. Focused tests use actual Unicode control scalars in curved scene/one-native-fill/selection and next-hue assertions. Ordinary unmarked Latin curves, scripts, font loading, canonical recipe, Undo and renderer/worker/export source remain unchanged. No claim of a full Bidi visual-run colour resolver or Android/IME acceptance.

## T4g · No-Segmenter Unicode integrity at the 160-codepoint boundary, 26 October 2026

**Merged [#745](https://github.com/gamesbyian/wallgen/pull/745), Node fallback tests and [quick CI green](https://github.com/gamesbyian/wallgen/actions/runs/40369763242).** Reproduced source-level data-loss edge: #688 protected complete `Intl.Segmenter` graphemes on supported browsers, but in a runtime without that optional API `boundTextContent` iterated each Unicode scalar separately. `159×A + e + combining acute` could save `159×A + e` without its accent, and `158×A + 👩‍🚀` could save only part of the joined emoji at the 160-codepoint boundary. The straight, native-shaped text renderer cannot recover deleted source characters after normalization. The same fallback undercounted/overcounted per-letter rainbow colour cycles by fragmenting joined emoji and regional flags. A bounded *lazy*, conservative fallback cluster iterator now groups following Unicode marks, emoji modifiers, ZWJ sequences, emoji tag controls and regional-indicator flag pairs. It is used only when `Intl.Segmenter` is unavailable; normal modern browser codepath and output are unchanged. The canonical 160-codepoint/4-line budget still counts actual Unicode codepoints and never serializes half of these common user-owned clusters.

**Scope and limitations:** This is targeted grapheme integrity for common emoji/accent sequences, **not a full Unicode UAX #29 implementation** or a claim of complex-script font correctness. Unsafe contextual joining on arbitrary curves continues the native whole-line fallback; unknown old-browser/native OS emoji appearance remains externally untested. Targeted tests simulate no Segmenter, check at-limit recipe/JSON stability, safe fallback word/letter colours and basic ASCII unaffected. No new font assets, network fetch, recipe version, worker rasterizer, UI focus/IME behavior or long-running browser CI. Normal quick suite is sufficient for a pure bounded-text path correction.



## T4f · Truthful per-object curve fallback disclosure, 26 October 2026

**Merged [#744](https://github.com/gamesbyian/wallgen/pull/744), Node status tests and [quick CI green](https://github.com/gamesbyian/wallgen/actions/runs/40369068476).** Observed inconsistency, corrected by the scoped UI text fix: Existing Text → More options → Text baseline status promises an authored Draw path is being used merely when two saved Draw points exist. But the *actual* compositor refuses paths shorter than 35 design units or unavailable after normalization. Moreover, contextual Arabic/Indic/RTL input deliberately paints straight to protect native shaping while the old panel displays only generic, non-specific curve help or a false "Using the authored Draw path" message. In a mixed English/Arabic multiline object, only some lines can bend. The fix derives the selected object's status from the same `canCurveText` and `prepareTextFollowPath` contracts as the renderer, without creating a second shape engine. It states exactly when all or some lines are native straight fallbacks and explicitly that the user's authored baseline choice is preserved. A real valid Draw path retains the existing correct instruction. Tests cover straight, valid/invalid two-point Draw, Arabic contextual fallback, mixed line count, ZWJ emoji curve support, and the live aria-live path status node.

**Risk and boundary:** Pure disclosure logic only, same existing UI status element, no additional focus/scroll/IME events, no text-content mutation, no recipe/Undo change and **zero wallpaper pixel changes intended**. No claim that native complex glyphs now follow arbitrary curves. Short labels are for a selected authored object, not a promise of OS font coverage or Android TalkBack approval. Focused Node and ordinary lean CI suffice; no automatic browser screenshot workflow.



## T4e · Dual-ring outline ink and selection geometry, 26 October 2026

**Merged [#742](https://github.com/gamesbyian/wallgen/pull/742), geometry/painter tests and [quick CI green](https://github.com/gamesbyian/wallgen/actions/runs/40368476587).** Specific reproduced source defect: optional black–white/white–black letter outlines paint their *outer* stroke at 2.5× the inner line width, but the shared canvas pick, generic pick and transform-guide frame had only allowed an unscaled inner-width margin. A 180-unit glyph with 20% outline paints a 90-unit outer stroke, which extends 45 units beyond its glyph path; the prior selection margin was only 36, leaving up to 9 canonical units of painted ring untouchable. At small sizes the discrepancy is proportionally smaller but still relevant near 44px handles. A tiny shared pure reach helper keeps the renderer's original 2.5× width exactly and preserves the historically generous single-ring selection extent. The three selection/guide call sites use the same outer-ring reach. Tests cover both outline orders, prior missed painted edge, beyond-ink miss, circular glyph pick vs hollow centre and actual existing stroke calls.

**Acceptance limit:** This aligns deterministic approximate advance-box hit geometry with the visible stroke *width*. It does not claim pixel-perfect glyph contours or physical touch acceptance, and the painter's output is intended to remain unchanged. Final-head quick CI passed and PR is merged. #664 is already closed following independent Chromium software acceptance; actual handset/human/IME/TalkBack remain external owner tasks.



## Agent 2 T4d: font-tracking capability and transform guide parity · 25 October 2026

**Merged [#733](https://github.com/gamesbyian/wallgen/pull/733), focused Node and lean CI accepted.** The painter and #729 hit selection correctly leave authored `letterSpacing` dormant on a Canvas implementation with no native `ctx.letterSpacing` property. But existing `measuredTextBounds` always added the recipe's letter spacing to its untracked width when positioning the visual selection frame and compact 44px transform handles, causing the editor guide to claim a wider shape than actual ink. This is a deterministic capability-mismatch case, not a confirmed physical handset failure. The pure bounds helper now accepts an optional `nativeTracking` flag defaulted to the established supported-browser semantics; the real text editor passes its actual canvas context capability. With a four-letter 48-unit natural line and 14-unit tracking, supported guide width stays **104**; a mocked unsupported context correctly yields **48** (formerly 104), including curved guide mode. Source tests check the real UI propagation. No recipe change, font load, renderer, worker, export or Undo change; no impact to Pixel Chromium environments where native tracking is available. Device-specific native Canvas support and human direct-touch testing remain unverified and Agent 3-owned.
