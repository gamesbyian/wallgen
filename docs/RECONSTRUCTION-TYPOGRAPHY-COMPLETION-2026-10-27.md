This page is the **small current exit contract**, not a new research queue, alternative product specification, or numerical universal-image-quality guarantee. ## Decision 1: Typography feature is software-complete, with a disclosed optional advanced feature

**Core feature acceptance: PASS within its evidenced software/Chromium scope.** Canonical editable text; true on-canvas moving/scaling/rotating; black/white, per-word/per-grapheme rainbow and whole-text effects; dual outlines and directional shadows; 27 pinned licensed bundled fonts and private TTF/OTF lifecycle; straight and ordinary curved path text; Unicode/grapheme preservation; local persistence, explicit portable fonts; synchronous Undo, locks/randomize and current PNG/JSON round trip; shared direct/worker/headless 3024×6552 export have already been demonstrated in prior source and actual Chromium evidence, including [13 multilingual direct/worker PNGs](https://github.com/gamesbyian/wallgen/actions/runs/40385281268), [full-size private font export](https://github.com/gamesbyian/wallgen/actions/runs/40137771056) and [real portrait same-ID async-import race](https://github.com/gamesbyian/wallgen/actions/runs/40435480291). These are actual app/renderer software tests, not physical Android certification.

**Deliberate supported-mode limitation:** for contextual Arabic, Indic, complex mixed-Bidi and other joining/shaping-dependent strings on arbitrary curves, prefer complete native-shaped straight-line fallback, preserve edited path choice for future reuse, and explain why visibly. Never split a shaping run into independently painted code points and label the result correct. Current Canvas2D `TextMetrics` returns aggregate dimensions, not a reliable run of positioned shaped glyphs. Full arbitrary-curve complex-script shaping is an **optional later feature request requiring concrete demand and a bounded proof**, not a blanket acceptance blocker for the delivered text overlays.

**Closure rule for #653:** If current main's targeted tests, prior real browser/PNG evidence and UI fallback explanation stand, close **#653 as completed for its original owner-visible typography feature**, explicitly excluding unsupported native joining-script curved layout and unperformed device/human checks. Reopen *only* for a new reproducible regression to an advertised working feature; create a specifically scoped future enhancement **only after** a real supplied use case. Do not keep #653 open awaiting unattainable abstract completeness, generic emoji font consistency between operating systems, or physical testing not performed by an agent. A release evidence ledger separately records physical Pixel Chrome/PWA, Android IME/TalkBack, human type aesthetics and sustained export/thermal usage as NOT TESTED.

**If multilingual curved layout is specifically requested, external route:** first reproduce a concrete failure on a pinned, redistributable font and an author-selected Draw/Hairpin/Loop path. Compare browser-native SVG `<textPath>` (native shaping, but image/canvas/worker/font/privacy parity must be measured) with **HarfBuzz / harfbuzzjs** (returns shaped glyph IDs, cluster boundaries, advances and offsets) plus an existing, licensed glyph-outline reader if actually needed. Test right-to-left, clusters, combining accents, font fallback, original private face bytes, variable/colour glyphs, worker/headless, path hit-testing, memory/first-load time and native PNG parity. Stage in an opt-in experimental path, do not vendor enormous WASM binaries, rewrite the compositor, invent Unicode ordering, or advertise it without rendered visual evidence. OpenType.js can provide vector outlines; its shaping should **not** be assumed equivalent to HarfBuzz for all scripts. No new library is approved for unconditional production dependency by this research memo.

## Decision 2: Reconstruction is a bounded usable image→editable-current-recipe converter

**Success is an honest, useful current editable representation of _visible_ source evidence**, not retrieval of the original generator internals. There are two valid success paths: (A) source-visible independently editable imported paths/shapes/geometry, and (B) recognizable present-day procedural recipe. A 7-hue composition with visible occlusion can preserve visible contours and gaps without inferring invisible continuation/over-under order; it may disclose ambiguous topology. If the model cannot express a seen hue slot, colour, stacking order or silhouette, reject automatic full-fidelity claims and offer manual geometry import/correction. Absence of a credible candidate is a successful **truthfulness decision** on unsupported source art, not an inverse-fit software failure.

### Normal #557 software-exit rubric

1. **Truth and repeatability (mandatory).** Source PNG/JPEG/SVG original bytes immutable; source/provenance distinct from inferred recipe; zero fabricated hue slots or hidden authorship; accessible partial/refusal notice and practical manual route; lock-safe Apply, single Undo, edit, save and visible PNG/JSON reimport. Preview/export uses present-day canonical `normalizeRecipe`/scene/shared renderer with no inverse-only dialect.
2. **Current source fidelity (mandatory for the claimed supported classes only).** Run a fixed representative current-renderer suite (already available: 22 R0 sources) plus truly independent author-created controls from the existing 16-image external set, including simple bands, holes/islands, open frame edges, overlapping distinct colours and false-positive traps (low-chroma, dark, sparse/skipped hue). Use identical input art for old/new. Inspect actual source, proposed image and a native-size crop around the claimed failure. Compare **within the same scorer version** using full-pixel RGB/ink difference, local edge/negative-space and hue-slot/topology checks; metrics guide review, never universally dictate visual beauty. Require no material loss of already-proven supported cases, and no new false colour-faithful candidate on explicitly unsupported controls. A pixel-identical non-change is fine; avoid demanding endless tiny global-score wins.
3. **Targeted residual problem.** Work on one independently reproducible *visible* occlusion, Hairpin/Loop void, disconnected ribbon or source contour defect at a time. Before fitting, state whether the current scene can represent it; otherwise document/refuse. A change qualifies only with before/after original and fitted **real painter** PNG, visible local improvement plus meaningful metric/topology validation, controls, determinism, source safety and no extra normal paint requests. Reject heuristic threshold drift, invisible branch guesses and slight score wins whose native-sized visual quality is worse.
4. **Time and computational ceiling.** Preserve the existing **up to six initial plus ten refinement** actual render evaluations, latest-only/cancellation/locks and privacy defaults. Retain tiny quick unit tests by default; one-shot real-browser imaging only for a new high-value demonstrated source defect. Track time-to-useful editable candidate on a representative browser as observation, not a promised Pixel millisecond target.
5. **Stop condition.** Once the above holds for the product's declared supported source classes and remaining mismatches are **ambiguous/unsupported** or merely below meaningful visual impact, close #557 as software feature-complete with explicit known limits. Failure on arbitrary photographs, sophisticated materials, suppressed tones, missing hue slots, impossible back-of-object geometry, original seeds, or unknown historical renderer generations is **not** grounds to reopen. A new independently supplied representable counterexample **with visible, fixable harm** may justify one separate focused ticket.

**Current evidence boundary:** [#804 real-source contour A/B](https://github.com/gamesbyian/wallgen/actions/runs/40440144304) and [#806 38-source paired A/B](https://github.com/gamesbyian/wallgen/actions/runs/40442935241) improved supported cases without regressions in those sampled corpora; [#805 native Hairpin/Loop](https://github.com/gamesbyian/wallgen/actions/runs/40441481288) demonstrated 3024×6552 worker/reference exactness and visible residual local stairsteps. Those residual visible contours are the **one remaining specifically evidenced quality discussion**; new work needs meaningful real 4K-visible improvement and a fresh independent source, not a theory-only optimization. Human/owner art evaluation and physical Pixel acceptance remain separate.

### Outside tools: use an oracle, not a replacement renderer

- **Existing opt-in VTracer evaluation is already present**: `scripts/benchmark-reconstruction-vtracer.py`, `scripts/benchmark-reconstruction-vtracer.mjs` and `tests/reconstruction-vtracer-oracle.test.js`. Reuse it; do not duplicate a second vectorizer benchmark. [VTracer v1 open core](https://github.com/visioncortex/vtracer) now documents separate segmentation/curve stages, cutout (shared boundary/seam-free), stacked layering, fixed-palette/OKLab snapping and watershed controls. Its Rust/Python/Node API may help answer whether difficult visible negative-space contours need improved segmentation. **Pin version, verify license and use isolated research first**: a prettier SVG is neither the original source nor an editable canonical ROYGBIV recipe. A result with hundreds of generic paths is not a successful model integration.
- For a narrow hole/connected-component failure, established [OpenCV contour hierarchy](https://docs.opencv.org/4.x/d3/dc0/group__imgproc__shape.html) (`RETR_TREE`) is a useful independent analysis oracle. Check topology separately from mean pixel error. The existing repo already has mask/component/hierarchy code; do not add heavyweight OpenCV/WASM to the shipped PWA without clear measured value.
- Alternative [ImageTracerJS](https://github.com/jankovicsandras/imagetracerjs) has permissive public-domain code and may be a small additional research baseline, but adds no visible value until VTracer/current import fail a specific measured case.
- **Avoid learning-based image generators/inpainting** to guess invisible stripes; plausible hallucination would silently change the source's semantics. Never use external upload/service for owner/private source art without explicit consent.

| Text product feature | Canonical/UI/Undo/worker/real image evidence and honest native-straight fallback | Arbitrary curved joining-script research, actual Android IME/TalkBack, physical performance, creator judgement |

**Operational guard against an endless research programme:** one failing original image, one falsifiable proposed cause, one existing canonical module, one before/after, one targeted validation and one PR. If a follow-up cannot state an actual source-visible defect, defer it instead of launching another opaque 20-run campaign. Do not conflate exploration studies with mandatory shipment criteria.
